# Общие принципы работы — Real Estate Marketplace

## Что это за проект

Pet-проект коммерческого уровня для портфолио (цель — позиция strong middle+ frontend/fullstack).
Демонстрирует осознанное применение GoF/GRASP/SOLID, DI и модульную архитектуру NestJS, доведение
проекта до реального деплоя на бесплатном хостинге.

Стек: Next.js 16 (App Router) + NestJS, монорепо Turborepo, TypeScript strict mode везде.

## Жёсткие правила

1. **Скоуп v1 зафиксирован** в `02-roles-and-scope.md`. Ничего из раздела Roadmap не реализуется,
   не импортируется как зависимость, не создаётся "на будущее" (никаких заготовок под Stripe,
   i18n-инфраструктуры, AI-функций и т.д.), пока явно не будет сказано, что v1 задеплоен и скоуп расширяется.
2. **Production-ready код, без плейсхолдеров и заглушек.** Если чего-то не хватает для полной
   реализации (переменная окружения, схема, тип) — не придумывать произвольно, а явно написать
   вопрос/TODO с описанием, чего не хватает, и остановиться на этом месте, а не додумывать логику.
3. **Не хардкодить текст глубоко в бизнес-логике** (см. локализацию в `02-roles-and-scope.md`) —
   строки пользовательского интерфейса держать в одном месте (константы/объект переводов), даже
   без реальной i18n-инфраструктуры в v1.
4. **Комментарии в коде — только если явно попросили.** По умолчанию код без комментариев.
5. **Строгая типизация TypeScript**, без `any` без крайней необходимости (и если пришлось — писать
   почему рядом, а не молча).
6. **Zod-схемы — единственный источник правды** для валидации: пишутся в `packages/shared` и
   переиспользуются как в NestJS (`nestjs-zod` + `ZodValidationPipe`), так и в React Hook Form на
   фронтенде. Не дублировать одну и ту же схему валидации в двух местах.
7. **memory-bank**: в начале задачи — прочитай `.clinerules/memory-bank/progress.md` и
   `.clinerules/memory-bank/decisions.md`.
   В конце задачи — обнови progress.md (что сделано/что осталось) и, ЕСЛИ по ходу реализации
   пришлось принять решение, не покрытое .clinerules (00-05) — зафиксируй его в decisions.md
   с датой и коротким обоснованием "почему". Не дублировать в decisions.md то, что уже
   зафиксировано в .clinerules.
8. **Backend-изменения подтверждаются прогоном e2e.** Любое изменение в `apps/api` перед
   коммитом проверяется `npm run test:e2e` (из `apps/api`, при параллельных запусках — с
   `--runInBand`). Один только `nest build`/`tsc` проверкой не считаются: ошибки DI (нехватка
   провайдера, цикл зависимостей) всплывают только при старте приложения в тесте, сборка их
   не ловит.

## Паттерны — не встраивать вслепую

Перед реализацией **каждого нового модуля** (backend) или **новой фичи** (frontend) — сначала
явно сформулировать одним-двумя предложениями, какой паттерн из чек-листа ниже уместен и почему,
и только после этого писать код. Если ни один паттерн не подходит — так и написать
("паттерн не нужен, простая CRUD-логика") и не притягивать искусственно.

Чек-лист паттернов — см. `03-architecture-patterns.md`.

## Границы ответственности

- **Nest-контроллеры — тонкие.** Только маршрутизация, валидация через Pipe, делегирование в сервис.
  Никакой бизнес-логики в контроллере.
- **Information Expert (GRASP):** логика присваивается сервису, который владеет нужными данными.
  Например, изменение статуса объекта при бронировании — это ответственность `BookingsService`,
  а не `PropertiesService`, даже если меняется поле `Property.status`.
- **Импорты между модулями NestJS** — только через явный экспорт провайдеров из модуля.
  `AnalyticsModule` и `AdminModule` могут зависеть от доменных модулей (`PropertiesModule`,
  `BookingsModule`, `UsersModule`), но не наоборот — доменные модули ничего не знают об analytics/admin.
  Это правило жёсткое, чтобы не получить циклическую зависимость модулей.
- **Frontend (FSD):** импорты только сверху вниз — `views → widgets → features → entities → shared`.
  Никогда в обратную сторону.

## Если есть противоречие или неясность

Если в задаче не хватает данных для реализации, или спецификация противоречит сама себе —
**остановиться и задать конкретный вопрос**, а не выбирать вариант молча. Особенно это касается:
переходов статусов в БД, прав доступа (кто что может делать), edge cases по конкурентному доступу.

## Инфраструктурные риски, которые нужно держать в голове при реализации

- **Render free tier** засыпает — нужен keep-alive через GitHub Actions cron, настраивается сразу
  в CI, а не постфактум.
- **Upstash Redis free tier** — лимит на количество команд, не на объём. BullMQ (delayed jobs,
  очереди email) активно шлёт команды в Redis. Если это станет проблемой — запасной вариант:
  `@nestjs/schedule` cron вместо BullMQ delayed job для auto-cancel брони. Не переключать
  превентивно — только если реально упрёмся в лимит.
- **Neon (serverless Postgres)** — cold start при первом коннекте. Если станет проблемой —
  подключить Prisma Accelerate или PgBouncer для connection pooling.
- **UploadThing free tier** — сжимать изображения на клиенте перед загрузкой, не грузить оригиналы.

## Git-процесс

- Conventional Commits: `feat:`, `fix:`, `refactor:`, `chore:`, `test:`
- Ветки: `feature/*`, `fix/*`, `refactor/*` → merge в `develop`, релизы в `main`
- Даже в соло-разработке история коммитов ведётся как в команде — часть демонстрации в портфолио

## Context7

Перед реализацией кода, использующего Next.js App Router API, NestJS, Prisma,
BullMQ или nestjs-zod — сначала вызвать Context7 MCP (resolve-library-id +
query-docs) для актуальной документации, не полагаться на внутренние знания
о версиях этих библиотек.
