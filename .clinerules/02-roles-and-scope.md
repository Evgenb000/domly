# Роли и функционал v1 — Real Estate Marketplace

Скоуп v1 зафиксирован жёстко. Всё, что не входит в v1, уходит в Roadmap в конце файла и не
реализуется, пока v1 не задеплоен и не работает end-to-end.

## Роли и права

| Роль | Права |
|---|---|
| **USER** | смотреть объявления, избранное, бронировать, размещать объявления, видеть простую статистику по своим объявлениям (сколько раз посмотрели) |
| **REALTOR** | всё как USER + плашка "Риелтор" на профиле и объявлениях |
| **DEVELOPER** (застройщик) | всё как USER + плашка "Застройщик" |
| **ADMIN** | модерация объявлений и юзеров, полная аналитика/статистика по платформе, доступ к админ-панели |

RBAC реализуется через Nest Guards + кастомный декоратор `@Roles()`.

Назначение роли REALTOR/DEVELOPER — self-service: юзер сам выбирает роль в своём профиле, доступно
только при подтверждённой почте (`emailVerified: true`). Проверка документов/лицензий не
выполняется — вне скоупа пет-проекта. Плашка — это просто заявленный статус, не юридически
верифицированный.

## Функционал v1

### Auth
- Регистрация/логин email+пароль
- Подтверждение почты (Resend + BullMQ очередь)
- Google OAuth
- JWT (access + refresh токены)

### Объявления
- Три типа сделки: продажа / долгосрочная аренда / посуточная аренда
- Типы реализуются через discriminated union в Zod-схеме — разные поля для разных типов
  (например, посуточно: цена/ночь + мин. срок заезда; продажа: просто цена). Форма в UI
  динамически меняется по выбранному типу
- Категории объекта: квартира, дом, комната, гараж и т.д.
- CRUD с проверкой владения (редактировать/удалять может только автор или ADMIN)
- Фильтры: тип сделки, категория, цена (диапазон), площадь, район
- Сортировка: по цене, по дате
- Карта (Leaflet) с метками объявлений и кластеризацией

### Бронирование

**Полная спецификация статус-модели — в файле `05-booking-status-model.md`, читать его перед
реализацией модуля bookings.** Кратко:

- Применяется ко всем трём типам сделки (продажа / долгосрочная аренда / посуточная аренда) —
  не только к посуточной. Смысл единый для всех типов: юзер фиксирует за собой объект, пока
  договаривается с владельцем, чтобы никто другой не перехватил
- Простая заявка: юзер жмёт "забронировать" → статус объекта меняется `available → reserved`
- Пока объект в статусе `reserved`, другие забронировать не могут
- Снять бронь может: владелец объекта, тот кто её поставил, или ADMIN
- **Отдельного статуса "подтверждено владельцем" в БД нет.** Бронь просто держит объект в
  `reserved` 24 часа. Если за это время владелец (или инициатор брони, или ADMIN) не отменил
  бронь вручную — статус объекта автоматически возвращается в `available` по таймеру
  (BullMQ delayed job, `delay: 24h`, фиксированное значение для всех типов сделки в v1). Никакого
  отдельного действия "подтвердить" не существует — молчание владельца в течение 24ч не меняет
  ничего, просто по истечении таймера бронь истекает сама.

### Избранное
- Добавить/убрать объект в избранное, отдельная страница со списком

### Статистика
- USER: простой счётчик просмотров своего объявления. Инкремент атомарный на уровне SQL
  (`views = views + 1`), дедупликация повторных просмотров одним и тем же пользователем/сессией —
  через Redis (`SETNX` с TTL), чтобы обновление страницы не накручивало счётчик
- ADMIN: полноценная аналитика — количество объявлений/юзеров, динамика по времени, топ
  объявлений по просмотрам, воронка (просмотры → брони)

### Админ-панель
- Модерация объявлений (approve/reject перед публикацией)
- Управление юзерами (блокировка, смена роли)
- Дашборд аналитики (см. выше)

### Локализация
- Только украинский язык, без i18n-инфраструктуры в v1. Код писать так, чтобы вынос строк в i18n
  не был болезненным при необходимости позже — не хардкодить текст глубоко в бизнес-логике
