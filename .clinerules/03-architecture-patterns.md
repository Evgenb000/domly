# Архитектурные паттерны и структура папок — Real Estate Marketplace

## Паттерны — чек-лист по применению (GoF/GRASP/SOLID)

Применяются явно и осознанно, с умением объяснить "зачем" на собеседовании — не для галочки.

| Паттерн | Где применяется |
|---|---|
| **Repository** | слой поверх Prisma — абстракция доступа к данным, сервисы не знают о Prisma напрямую. Реальная польза здесь — не "смена ORM в будущем" (это маловероятно), а тестируемость сервисов через моки репозитория без поднятия тестовой БД |
| **Strategy** | алгоритмы сортировки/фильтрации объявлений; разные стратегии расчёта цены (продажа/аренда/посуточно) |
| **Factory** | создание разных типов уведомлений (email подтверждения, уведомление о брони, авто-отмена) |
| **Observer / Event Emitter** | события бронирования (создано/подтверждено/отменено) — Nest `EventEmitter2`, слушатели триггерят email и обновление статистики независимо от основной бизнес-логики |
| **Decorator** | Nest Guards/Interceptors для авторизации, логирования, кэширования ответов |
| **DTO + Mapper** | чёткое разделение Prisma-модели ↔ данные, отдаваемые наружу через API |
| **GRASP: Information Expert** | логика присваивается классу/сервису, который владеет нужными данными (например, `BookingService` знает, как менять статус объекта, а не `PropertyService` дёргается извне) |
| **GRASP: Controller** | Nest-контроллеры — тонкие, только маршрутизация и делегирование в сервисы, никакой бизнес-логики |
| **GRASP: Low Coupling / High Cohesion** | модульная структура Nest (один модуль = одна зона ответственности: `auth`, `properties`, `bookings`, `users`, `analytics`) |
| **SOLID: Dependency Inversion** | сервисы зависят от интерфейсов репозиториев, не от конкретных реализаций (упрощает тестирование через моки) |

Правило: при каждом новом модуле явно проговаривать, какой паттерн уместен и почему, а не
встраивать искусственно.

## Архитектура папок — Frontend (Feature-Sliced Design, адаптирован под Next.js App Router)

`app/` остаётся только роутингом Next.js (тонкие файлы, импортируют View из `src/views`). Сама
FSD-структура — в `src/`:

```
apps/web/
  app/                      # роутинг Next.js — только page.tsx/layout.tsx, без логики
  src/
    views/                  # FSD-слой "pages", переименован во избежание конфликта с app/
    widgets/                # составные блоки (Header, PropertyFiltersPanel, PropertyMap)
    features/               # бизнес-фичи (add-to-favorites, create-booking, auth-by-google)
    entities/               # бизнес-сущности (property, booking, user) — модели, карточки
    shared/                 # ui-kit, api-клиент, хуки, utils, config
```

Правило: импорты только сверху вниз (`views → widgets → features → entities → shared`), никогда
наоборот. Это GRASP Low Coupling в чистом виде.

## Архитектура папок — Backend (Domain Modules, родная архитектура NestJS, не FSD)

FSD — фронтенд-специфичная методология, на бэкенд не переносится. NestJS уже даёт модульную
структуру:

```
apps/api/
  src/
    modules/
      auth/
      properties/
      bookings/
      analytics/
      admin/
      users/
    common/                 # общие guards, interceptors, decorators, filters
    infrastructure/         # Prisma-клиент, Redis, BullMQ конфиг
```

Один модуль = одна зона ответственности (High Cohesion), связь между модулями — только через
явный экспорт провайдеров (Low Coupling).

**Направление зависимостей между модулями (жёсткое правило):**
`analytics` и `admin` могут импортировать провайдеры из доменных модулей (`properties`,
`bookings`, `users`, `auth`), но не наоборот. Доменные модули ничего не импортируют из `analytics`
или `admin`. Это предотвращает циклические зависимости модулей Nest и держит доменную логику
независимой от аналитики/админки.
